# 代码审查标准与流程

> 本文在提交 Pull Request、评审 PR 或收到审查意见时按需读取。
> 涉及架构边界的审查项引用 `AGENTS.md` 稳定标识（如 `ARCH-KERNEL`），不得放宽对应规则。

## 一、审查定位与原则

代码审查的目标不是"找茬"，而是让合入 `main` 的每一行代码**正确、安全、可维护、可验证**，同时让作者在审查中学到东西。

四条基本纪律：

1. **具体**：指出文件与行号，说明问题是什么，而不是贴"这里有问题"。
2. **解释为什么**：每条意见必须给出理由，作者才能判断是否采纳。
3. **建议而非命令**：除非是 Blocker，否则用"建议/考虑"，把最终方案留给作者。
4. **完整反馈**：一轮审查给全所有意见，禁止分批小纸条式评论。

## 二、意见分级标准

所有审查意见必须带以下级别前缀，作者与审查人据此决策。

| 级别 | 含义 | 合入门禁 | 典型场景 |
|---|---|---|---|
| 🔴 **Blocker（必须修复）** | 不修复会导致事故或破坏既有契约 | 不得合入，直到解决 | 安全漏洞、数据丢失、架构边界破坏、API 契约破坏、关键错误处理缺失 |
| 🟡 **Suggestion（应该修复）** | 会显著影响质量，但当前不致命 | 合入前必须处理或明确回复"暂不处理及原因" | 输入校验缺失、命名/逻辑不清、缺关键测试、明显性能问题、重复代码 |
| 💭 **Nit（可选）** | 风格与细节优化 | 可合入后补 | 命名微调、注释补充、格式一致性 |

**判定优先级规则**（冲突时按此顺序）：

1. 影响用户数据（丢失、损坏、外泄）→ 一律 Blocker。
2. 破坏 `AGENTS.md` 铁律 → 一律 Blocker，除非已获用户书面豁免。
3. 线上可被触发的错误路径 → Blocker；仅理论路径 → Suggestion。
4. 自动化门禁（lint/测试）能抓的 → 不需要人工重复评论，标注"应被门禁拦截"并让 CI 说话。

## 三、通用审查清单

所有改动都要过一遍，重点看本次 diff 涉及的部分。

### 正确性

- [ ] 边界条件：空值、空数组、超长输入、并发调用、重复提交（幂等性）。
- [ ] 错误处理：异常路径有兜底，不会吞掉错误也不会上抛到 UI 崩溃；失败有日志与可观测性。
- [ ] 状态一致性：异步完成后状态同步、加载/错误/空态三态齐全。
- [ ] 时间与时区：与时间相关逻辑是否依赖服务器时间、有无时区假设。
- [ ] 迁移兼容：旧数据、旧调用方是否仍然可用（见 `CHANGE-SAFE`）。

### 安全

- [ ] 输入校验：所有外部输入（用户文本、文件、网络响应、插件数据）在边界清洗与类型收口。
- [ ] 注入与 XSS：禁止将不可信输入直接拼进 SQL、HTML、URL 或 `eval`；本项目历史上有 SSRF 与 Zod 兼容性教训（见 `tests/suites/security.test.ts`、`tests/suites/architectureBoundaries.test.ts`）。
- [ ] 秘密管理：无 API Key、令牌、凭据写入源码或 `VITE_*` 公开配置（`CONFIG-TRACKS`）。
- [ ] 权限与边界：RPC、Native Adapter、插件 Host 的权限校验是否在正确层级。

### 可维护性

- [ ] 命名自解释；函数单一职责；重复代码是否该抽取。
- [ ] 文件行数 ≤ 1000 行（`QUALITY-TYPES`），接近阈值按职责拆分。
- [ ] 无显式 `any`（历史豁免点除外）；类型收口清晰（`QUALITY-TYPES`）。
- [ ] 注释解释"为什么"而不是复述"是什么"；删除死代码。
- [ ] 新增依赖是否必要；版本是否锁定（`package-lock.json` 更新）。

### 性能

- [ ] 循环内无重计算、无 `await` 串行化可并行的请求。
- [ ] 高频路径（渲染、输入、消息管道）无多余分配与泄漏（事件监听器、定时器清理）。
- [ ] 大列表/大数据量是否分页或虚拟滚动（项目已用 `@tanstack/react-virtual`）。

### 测试

- [ ] 行为变化有对应测试；修复有回归测试（先红后绿原则）。
- [ ] 测试符合 `TEST-CONTROLLED`：可复现、不依赖外部 CDN、不点按浏览器、超时受控。
- [ ] 测试不是脆弱的快照/实现细节耦合；断言行为而非内部实现。
- [ ] 本地验证范围符合 `docs/agents/development_workflow.md` 测试选择矩阵。

## 四、项目专项审查清单（绑定 AGENTS.md 铁律）

| 标识 | 审查时必查 |
|---|---|
| `ARCH-KERNEL` | 新代码是否污染 `src/kernel/`？业务、存储、UI、平台调用是否越界进入 Kernel？ |
| `ARCH-FLOW` | 页面/Hook/Context/领域规则是否直连 IndexedDB 或 `src/utils/localDB.ts`？事务与跨 Service 编排是否进了 `application/useCases/`？ |
| `COMPAT-DATA` | 是否把行为引导、破限或生态特例硬编码进通用系统代码？外部输入是否在边界清洗、类型收口、可降级？ |
| `PLATFORM-MOBILE` | 文件保存/Safe Area/状态栏是否走 Native Adapter？新代码是否假设普通浏览器行为在 WebView 可用？ |
| `CONFIG-TRACKS` | 配置是否进了正确的类型化入口？是否引入新的环境变量直读？`VITE_*` 是否被误放秘密？ |
| `QUALITY-TYPES` | 是否新增 `any`？类型是否用 `unknown`/窄化/泛型/Zod？模块边界是否退化？ |
| `CHANGE-SAFE` | 数据模型/Props/配置/API 变更是否有迁移与降级？旧调用方是否静默损坏？ |
| `TEST-CONTROLLED` | 验证手段是否符合仓库内测试优先？有无一次性点按或无界重试？ |
| `DOC-CHINESE` | 文档是否中文？是否在正确位置保持单一来源？ |
| `COLLAB-IDENTITY` | 版本号是否通过 `npm run bump-version` 修改？ |

按改动领域补充精读下列专项文档：运行时边界（`runtime_boundaries.md`）、配置策略（`configuration_strategy.md`）、类型纪律（`typescript_discipline.md`）、隔离开发（`isolation_development.md`）、移动端（`mobile_strategy.md`）、云端（`cloud_strategy.md`）、SillyTavern 兼容（`sillytavern_compat.md`）。

## 五、自动化门禁与人工审查分工

自动化负责"可机械判定"的部分，人工负责"需要判断"的部分。**自动化能抓的，人工不重复评论。**

| 层级 | 机制 | 判定内容 | 何时触发 |
|---|---|---|---|
| 提交前 | `.githooks/pre-commit`、`pre-push` | 类型检查；推送内容分类与门禁选择 | 每次 commit / push |
| 推送前 | `npm run quality:push` / `quality:release` | 普通改动执行完整门禁；可证明的纯版本提交只检查版本一致性 | 每次准备推送 |
| CI | `.github/workflows/quality.yml` | `lint` + `test` + `build` + Playwright E2E | 每次 PR 到 `main` |
| 按范围 | `check:i18n`、`verify:preset-samples`、`check:mobile-assets`、`cargo test`（云端） | 专项完整性 | 改动涉及对应领域时 |
| 人工 | 本节清单 + 第四节专项清单 | 设计合理性、边界、可维护性、测试质量、自动化覆盖不到的 | 每次 PR 合入前 |

**门禁纪律**：CI 未绿不得合入；CI 失败原因必须查明，禁止"关掉检查硬合"。Blocker 未清零不得合入。

## 六、PR 审查流程

```
分支创建 → 本地验证（hooks + quality:push）→ 开 PR（模板）→ CI 门禁 → 人工审查（多轮收敛）→ 合入 → 收尾
```

1. **分支规范**：从最新 `main` 拉取；AI 工具分支带 `codex/` 前缀，人工分支用 `feature/`、`fix/`、`chore/` 前缀；分支名含 Issue 号（如 `fix/142-retry-storm`）。
2. **本地验证**：按 `development_workflow.md` 测试选择矩阵完成最低验证；推送前跑 `quality:push`（或与改动范围相称的等价命令）。
3. **开 PR**：使用 `.github/PULL_REQUEST_TEMPLATE.md`；标题用语义化前缀（`feat:`/`fix:`/`refactor:`/`chore:`）；关联 Issue 与 Milestone。
4. **CI 门禁**：等待 `Quality Gate` 绿；失败先自修，不理解的失败在 PR 里提问而不是重试碰运气。
5. **人工审查**：
   - 审查人 24 小时内给出首轮完整意见；
   - 作者对每条意见响应：修复 / 说明原因后暂缓 / 反驳（附理由）；
   - 意见全部收敛后，作者重新请求审查，审查人做最终确认；
   - 大型改动按第七节分批。
6. **合入**：Squash merge 保持 `main` 历史整洁；commit message 与 PR 标题一致；涉及版本号走 `npm run bump-version`。
7. **收尾**：合入后由合入人关闭关联 Issue、勾选 Milestone、清理已合入分支。

## 七、审查规模分级

| 规模 | 判定 | 处理方式 |
|---|---|---|
| 小型 | 单一关注点，< 200 行改动 | 单一审查人快速过，聚焦三、四节清单 |
| 中型 | 200 ~ 1000 行，或跨 2~3 个模块 | 完整清单审查，作者附自测记录 |
| 大型 | > 1000 行，或跨层（Kernel/应用/基础设施） | **必须拆分 PR**；分批次审查；架构影响先在 Issue 讨论设计再动手 |

超过 1000 行的单文件改动（`QUALITY-TYPES`）视为架构信号，审查时特别关注拆分方案。

## 八、审查意见写法

**格式**：

```
🔴 **标题：一句话问题**
文件:行号 + 问题描述

**为什么：** 可能引发的后果

**建议：** 具体改法（代码示例或方案）
```

**反例**（禁止）：

- ❌ "这里写法不对" —— 不具体、无理由。
- ❌ "应该用 X 模式" —— 不解释为什么 X 更合适。
- ❌ "加个测试吧" —— 不指出哪个行为、什么用例。

**鼓励**：遇到清晰实现、巧妙解法、到位测试时明确表扬——审查也是团队学习机制。

## 九、审查人职责与节奏

- 项目规模较小，**任何合入前至少有一名非作者或 AI 审查通道完成一轮**；个人项目可用 CI 门禁 + AI 审查（如 code-review 专家）兜底，重大变更仍建议人工二读。
- 审查人只对"本次 PR 的范围"负责；发现既有问题可提 Issue，不在本 PR 无限扩大。
- 一轮意见必须完整；回复迟滞不超过 2 个工作日。
- 审查意见出现分歧时：作者说明理由 → 审查人重新评估 → 仍不一致则升级到 Issue 讨论，禁止在 PR 里僵持。

## 十、复盘与改进（轻量）

- 审查中发现的有争议或遗留问题，按既有惯例归档到 `docs/history/CODE_REVIEW_YYYY-MM-DD.md`（历史记录），标准与流程本身只维护在本文——二者职责分离，避免双份权威。
- 每次发版前回顾本轮 PR 的 Blocker：是否为同类问题重复出现？若是，补充自动化门禁或专项清单。
- 定期观察：意见是否集中在某几类（如 `any`、错误处理、测试缺失），针对性做小改进。
- 本项目为个人开源项目，不引入复杂度量指标；**闭环率（意见→处理）与 Blocker 归零**即为合格线。
